The one loss

Scanned Chinese page: 0.338 s vs 0.297 s

On the single-page scanned Chinese document, LiteParse finishes about 41 ms (14%) sooner. That is the only metric out of 162 where spdf is behind. On the same document spdf reads the text correctly (score 1.00 vs 0.04) and uses less memory (67.0 MB vs 85.5 MB). spdf runs a larger CJK recogniser on Chinese lines, which costs time.

OCR

Scans are read by a neural OCR engine compiled into the binary

PaddleOCR's PP-OCRv5 detection and recognition models, compiled to native Rust with Burn. spdf runs OCR automatically when a page has no text layer; --no-ocr turns it off.

Detect, orient, recognise

Text lines are detected, the page's reading direction (0/90/180/270° plus skew) is estimated, and each line is recognised along its own rotated box, so tilted and sideways scans come out as straight text with word boxes.

  • 0.990OCR text accuracy (NID)LiteParse 0.749
  • 0.367 smean time per scanned PDFLiteParse 0.474 s
  • 57 MBmean peak memory on scansLiteParse 90 MB

CPU, wgpu or CUDA

Short scans run on the CPU, where start-up is cheapest. Long jobs use the GPU through wgpu (Vulkan, DX12, Metal). Force a backend with SPDF_OCR_DEVICE=cpu|wgpu|cuda; CUDA needs the neural-ocr-cuda feature.

Weights embedded at build time

Model files are downloaded once, checked against pinned SHA-256 hashes, cached in %LOCALAPPDATA%\spdf\models (Windows) or ~/.cache/spdf/models, and compiled into the binary. Nothing to install at run time.

Quickstart

From zero to parsed PDF

The benchmarked build is main. It needs a current stable Rust toolchain (rustup update stable). The first build downloads PDFium and the OCR models, then compiles them in. The crates.io release (0.2.0-alpha.2) predates the built-in OCR engine.

  1. Install

    Builds the spdf binary from main with OCR included.

    cargo install --git https://github.com/Fanaperana/spdf --locked spdf-cli

  2. Parse

    Text by default; Markdown or JSON with --format. Output goes to stdout unless you pass -o.

    # layout-preserving plain text (default)
spdf parse report.pdf

# Markdown: headings and tables
spdf parse report.pdf --format markdown -o report.md

# JSON with a bounding box for every text item
spdf parse report.pdf --format json -o report.json

  3. Scans and OCR

    Image-only pages are OCR'd automatically. Nothing extra to install.

    # OCR is on by default for pages without a text layer
spdf parse scan.pdf --format markdown

# born-digital PDF? skip OCR entirely
spdf parse report.pdf --no-ocr

# pick the OCR backend explicitly
SPDF_OCR_DEVICE=wgpu spdf parse long-scan.pdf

Also: --target-pages 1-3,7, --password, --detect-tables, --stream, spdf batch-parse in/ out/, spdf screenshot. Run spdf parse --help for the full list, or use the Rust library API.

Methodology

How the numbers are made

  • Corpus. opendataloader-bench: 200 real PDFs with Markdown ground truth (reading order NID, tables TEDS, headings MHS), plus 46 generated edge cases: multi-column, rotated pages, RTL and CJK scripts, encrypted and corrupt files, image-only scans and a 400-page document.
  • Process. Both engines run through their CLIs, one process per document, so start-up and model load are included. One untimed warm-up, then the median of 3 runs.
  • Memory. Peak RSS is the larger of polled RSS (including child processes) and the process's exact peak working set.
  • OCR engines differ. LiteParse 2.19.0 uses bundled Tesseract on the CPU; spdf uses PP-OCRv5 on Burn. Same inputs, same default invocation, same machine.
  • Bands. A result within the noise band is a tie (0.0005 on accuracy aggregates, 3% on time and memory). A change is only accepted if no spdf metric regresses.
